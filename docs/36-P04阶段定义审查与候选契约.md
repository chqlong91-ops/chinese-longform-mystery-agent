# P04 阶段定义审查与候选契约

## 1. 审查结论

P04 有必要设立，但不应继续扩充授权文书、手工状态对象或单一小说的反复试跑。P01 已证明案件设计闭环，P02 已证明逐章规划与正文生产闭环，P03 已在 C10 上证明全书生产、长程一致性、唯一装配、整书审计和关键变化能力，P03-R1 已修复三级权限、唯一状态源、原子事务和 Skill-aware recovery 的产品控制面。

当前真正未被充分证明的是：这些能力能否由一个可执行编排器在全新项目中低交互运行，能否跨不同悬疑结构稳定复用，能否在真实项目载荷下恢复，并能否让用户只处理创意决定而不再处理内部事务。因此建议把 P04 定义为：

> **P04：可执行创作编排与跨项目泛化验证**

本文件是待用户确认的候选阶段契约。它完成 P04 定义审查，但不启动 P04，不创建 P04 子任务，不准入任何新小说项目。

## 2. 与既有阶段的关系

P04 是继 P03 和后置修复阶段 P03-R1 之后的下一主阶段，不是 `P03-S11`，也不是 `P03-R1-S09`。

- P01 提供 truth-first 案件设计、知情权限、公平线索、嫌疑管理和双重结局。
- P02 提供章节合同、场景规划、正文候选、审计、确认、formal 和结构同步闭环。
- P03 提供全书对象、批次生产、长程索引、分幕审计、唯一 ASM、整书审计、关键变化和终态恢复。
- P03-R1 提供三级权限、canonical registry、原子事务、生成视图、Skill-aware manifest、恢复运行时和 legacy 隔离。
- P04 不重定义上述方法；它把这些能力编排成可运行产品，并用新的异质项目验证泛化。

P03 的历史裁决继续保持 `9/11 satisfied / not-passed`。P04 的通过不能追溯改写 P03，也不能把 C10 的状态外推给新项目。

## 3. 阶段目标

建立并验证一个可执行、低交互、可观测、可恢复的“中长篇中文悬疑小说创作 Agent”运行形态，使其能够：

1. 从新的故事种子初始化隔离项目，而不是依赖既有正文或旧会话记忆；
2. 自动编排 P01→P02→P03 的常规路径，内部 permit、lease、hash、门禁和 checkpoint 不再转化为用户审批；
3. 在用户只处理创意方向、正文候选和真正 Tier 3 例外的情况下，持续推进案件设计、章节生产、全书审计和恢复；
4. 在至少两个结构、题材压力或叙事机制不同的新试点上验证同一协议的可迁移性；
5. 对真实项目载荷完成 project-bound `L6-P` 恢复评价，并证明状态、稿件层和结构同步不会漂移；
6. 用可复现指标判断 Agent 是否从“内部 Alpha、可监督使用”提升到“可重复使用的产品级 Beta 候选”。

## 4. 验证策略

P04 采用“一深一广”的两个异质新试点，不复用 C10 正文作为新试点输入。

### 4.1 深度试点

从故事种子开始，完整走通案件设计、章节地图、逐章生产、跨章与跨幕连续性、唯一全稿装配、整书审计、用户全书确认、恢复和阶段验收。它负责证明端到端完整性。

### 4.2 广度试点

选择与深度试点在核心悬疑机制、社会压力、叙事结构或篇幅规划上显著不同的项目，从故事种子完成案件设计和全书生产计划，并完成一个具有真实跨章依赖的代表性生产切片、审计和恢复。它负责证明初始化、路由和协议迁移，不冒充第二部完整成书。

### 4.3 历史参照

C10 只作为冻结的历史参照数据，用于比较流程缺陷、交互成本和状态稳定性；不得读取或修改其正文，不把它计入“两项新试点”。

## 5. 范围

P04 应包含以下能力域：

1. 可执行项目初始化器：建立隔离目录、项目身份、稿件层、结构文件、canonical project registry 和恢复入口。
2. 可执行工作流编排器：按当前状态选择唯一主路由，自动推进 Tier 1/Tier 2 下游动作，在 Tier 2 内容确认和 Tier 3 例外处形成清晰停点。
3. 创作能力集成：调用 `craft-social-mystery`、`novel-writing` 和 `novel-project-strategy`，保持各 Skill 的职责与证据边界。
4. 真实生产运行：完成深度试点的全书闭环和广度试点的代表性跨章切片。
5. 项目级恢复：使用 Skill-aware manifest v2，在真实载荷下评价 `L6-P`，记录 actual reads、not-read、over-read、writes、assertions 和 context disposal。
6. 状态与失败控制：保持唯一 current、原子提交、视图可重建、source drift 和 partial write fail-closed。
7. 用户体验与运行指标：统计用户停点、无效授权请求、恢复耗时、状态漂移、重跑范围和人工修复量。
8. 跨项目泛化审计：比较两个新试点和 C10 历史参照，区分可复用能力、项目特例和仍未证明的能力。

## 6. 非目标

P04 不包含：

1. 继续修复、重审或重新授权 C10；
2. 为追求形式完整而增加新的逐动作授权、hash 长文或手工状态副本；
3. 开发图形界面、云服务、插件市场、多人协同平台或商业发布系统；
4. 模型微调、训练数据建设或对基础模型能力作无法验证的提升声明；
5. 自动决定核心因果、责任人、决定性线索、幕结构或结局等 Tier 3 创意事项；
6. 以目录存在、脚本全绿、用户泛泛认可或单一项目成功代替真实内容和恢复证据；
7. 声称出版质量、销量、法律结论、版权清白或对所有悬疑类型普适。

## 7. 入口条件

P04 只有在以下条件同时满足后才能启动：

1. 用户明确确认本候选定义及阶段名称；
2. P03-R1 frozen baseline 保持有效，canonical registry、原子事务和生成视图无漂移；
3. P04 父任务、coverage、验收对象和失败关闭规则被正式建立；
4. 两个新试点的异质性标准被先定义，之后再选择故事种子；
5. 新试点使用独立工作区，C10 和 P01—P03 legacy 保持只读；
6. project-bound `L6-P` 的 Tier 3 边界在阶段契约中保留，未获授权前不得向独立上下文发送真实项目载荷。

## 8. 候选验收标准

### P04-AC01 阶段与项目隔离

P04 阶段契约、两个新试点身份、目录、coverage 和 source-of-truth 唯一；不存在 C10、legacy 或两个试点之间的状态污染。

### P04-AC02 可执行初始化

两个新试点均可由统一初始化入口从故事种子建立合规工作区、稿件层、状态注册表、最小恢复包和唯一下一步，无需手工复制状态模板。

### P04-AC03 可执行编排

统一编排器能够依据 canonical state 选择 P01→P02→P03 的唯一主路由，自动执行允许的下游动作，并在失败后给出确定的 resume、repair、replan 或 stop。

### P04-AC04 深度试点完整闭环

深度试点从故事种子推进到逻辑成立、线索公平、正文可读、全书状态一致的 current 完整小说，并实际完成案件、章节、长程、装配、整书审计、确认和恢复门禁。

### P04-AC05 广度试点迁移闭环

广度试点完成案件设计、全书生产计划和代表性跨章生产切片；其悬疑机制或结构压力与深度试点显著不同，且没有通过复制项目特例冒充泛化。

### P04-AC06 悬疑与正文质量

两个新试点均通过与其实际范围相称的因果、信息权限、公平线索、嫌疑校正、现实命题、人物、场景、文风和安全审计；深度试点同时闭合事实结局与人的结局。

### P04-AC07 三级权限与低交互

内部 permit、lease、hash、A0—A5 和普通门禁产生的用户授权请求为零；用户停点只来自明确的 Tier 2 内容确认或 Tier 3 例外，并能由停点日志逐项解释。候选确认后的普通下游闭环由 Agent 连续完成。

### P04-AC08 真实项目恢复

深度试点至少在中段 checkpoint 和终态 checkpoint 各完成一次 project-bound `L6-P` clean recovery；广度试点至少完成一次与其范围相称的 project-bound recovery。每次均要求 Skill 依赖合法、over-read=0、状态重建正确、unique next 唯一。

### P04-AC09 状态一致性与原子性

全阶段不存在双 current、稿件层混同、确认/同步互相推断、视图反向授权或未登记 partial write；所有 current mutation 可追溯到原子事务，派生视图可确定性重建。

### P04-AC10 强制失败与选择性恢复

至少覆盖 source drift、依赖缺失、状态冲突、部分写入、越界读取、错误确认继承和跨项目污染等失败；均能 fail-closed，且只重跑受影响范围。

### P04-AC11 泛化与体验证据

形成跨项目对照，至少报告初始化成功率、常规路径自动推进率、用户停点构成、恢复成功率、状态漂移数、选择性重跑范围和项目特例数量；不得只用主观“好用”作结论。

### P04-AC12 诚实验收与基线

阶段报告明确区分已证明、未证明、research、ambiguity、risk 和 nonclaims。只有 AC01—AC12 全部 `yes/evaluated` 才允许创建 P04 frozen baseline；否则以 not-passed 闭合，不以降低标准换取通过。

## 9. 成功定义

P04 成功不等于“又完成一本小说”，而是证明同一 Agent 运行系统能够在新项目中重复完成创作闭环，并且：

- 用户主要参与创意与内容判断，而非内部事务授权；
- 项目可以从文件和 manifest 恢复，而非依赖长会话；
- 不同悬疑结构不会迫使系统退回手工文书编排；
- 内容质量、状态一致性和恢复能力都有实际证据；
- 失败时能够局部关闭、最小修复和选择性重跑。

满足这些条件后，Agent 才有资格从内部 Alpha 进入产品级 Beta 候选评估。
